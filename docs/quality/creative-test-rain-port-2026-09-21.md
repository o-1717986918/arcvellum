# 雨港离航创作实测报告（2026-09-21）

## 测试范围

本轮以普通创作者身份从 Studio 界面新建作品《雨港离航》，要求系统经正式路线完成一个可审阅场景。文风指定 R17 的雨夜离别、R21 的赛博都市氛围为主，R02 的关系观察为辅。R17—R25 全部按正向类型氛围与空间定调参考处理，不再标为反例。

测试要求包括：雨、霓虹、空港广播和倒计时必须介入行动与选择；周岑与许遥不直说不舍；正文仍接受现有违禁表达与中文标点审查；目标到第一场正式正文即暂停。

## 用户路径结果

- 新建、记录创作方向、启动长期目标、生成、审读、晋升和按检查点暂停均可从界面完成。
- 生成一场 2473 个中文内容字符的正式正文《旧城区记忆修复铺的交接》，提交回执与场景增量均已落盘。
- 顶层 Agent 在启动前能够先说明两位人物、核心冲突、预期变化和 R17/R21/R02 的参考机制；这部分符合普通创作者需要。
- 创作现场能看到生成、机器检查、审读、修订和入卷状态，但“机器检查通过”与实际违禁表达冲突，见下文。

## 正文评价

### 有效部分

1. 类型氛围已经进入行动层。雨影响供电和设备，广播改变离港信息，巡逻艇封锁原路线，倒计时迫使两人放弃主读机方案，霓虹与终端光参与可见性和关系距离。
2. 情感主要通过选择呈现。周岑保留备份的犹豫、许遥主动把接口送近、周岑拔掉主读机电源，都比直接写“不舍”有效。
3. 场景存在清楚的因果转折：东侧料场封锁，南口绕行增加时间，两人改用风险更高的直连方案，记忆与航线被绑到同一个失败后果上。
4. R17 与 R21 被作为正向机制使用，R02 提供了关系观察；没有复制参考语料的专名或连续句子。

### 仍显生硬的部分

1. 正文出现两处机械对照：“没有再往……推，而是拉开……”和“不再是等待，而是读取”。它们都属于现有核心违禁表达的同构变体，却通过了机器检查与审读。
2. 个别段落把潜台词解释完了。例如“周岑知道他知道答案”“有些事不必说透”先声明了两人默契，削弱了前后动作本来能够产生的余味。
3. 设备规则为情感选择服务得过于整齐。隔离层、缓存、短接缆和运行区在短时间内连续增加，读者能理解风险，却容易感觉技术设定是为当前抉择临时搭出的机关。后续应提前埋一条设备限制，或删去一层术语。
4. 后半段反复调用雨、广播、航线、终端、缆线，开始显出“逐项兑现需求”的痕迹。环境应继续改变局面，已经完成任务的意象不必再次点名。
5. 场景结尾有关系动作和风险升级，但记忆仍在传输，离航后果尚未发生。它适合作为章节开场，作为“可独立阅读的完整场景”仍少一段即时后果。
6. 最后以探照灯扫过交叠手背收束，画面清楚，但接近常见的模型式象征收尾。更有力的落点会是设备状态、路线代价或人物不可撤销的下一步。

## 顶层 Agent 回执问题

启动前说明合格，终态回执有三处事实偏差：

1. 正文始终用“他”指周岑，人物资料没有声明性别，回执却写成“她”。
2. 正文中两人已经选择短接缆并开始读取；回执沿用旧规划字段，称“交接没有完成、被迫考虑替代方式”。这把计划阶段的预期转折错当成了成稿结局。
3. 系统已有 `workflow/scene_deltas/scene_0001.json`，只是尚未晋升为持续的人物/连续性状态；回执直接说“没有连续性底账”过于绝对。
4. 回执连续使用“不是障碍，是……”“不是装饰”“不是一次通过”“不是字数问题”等自我纠偏句，呈现出核对要求的报告腔；文风名也从实际的“清简叙事”漂移成“清晰平实”。

根因是 `story_brief` 的已完成剧情只取 scene/rhythm 规划字段，没有携带最近正式正文证据；顶层 Agent 因而在里程碑回执里复述了陈旧计划。

## 修正

本轮不新增门禁层，只校准现有生成与审查链：

- 现有生成提示明确列入“不再是……而是……”和“没有再……而是……”两个实测变体，继续要求在生成阶段主动清理。
- 现有 Style Lint 的 `mechanical-contrast-frame` 补齐相同变体；违禁表达仍由既有审查链阻断，未改变软文风约束的处理位置。
- `story_brief` 只为最近一个已晋升场景附带限长的 `actual_prose_tail`，原场景转折改名为 `planned_story_move`，不再伪装成已经发生的结果。里程碑回执必须以正式正文证据优先，计划字段冲突时不得复述旧计划。
- 顶层 Agent 未取得明确人物性别时使用姓名或角色称呼，不自行补全。
- 顶层 Agent 的用户说明直接陈述故事事实，避免成串机械对照；未读取文风控制证据时不猜文风名称。
- 顶层 Agent 必须区分尚未开始、正在进行、已经失败和已经完成，避免把“传输已经启动”写成“交接失败”。
- `continuity_status=not_recorded` 的用户表述收窄为“尚未在连续性投影中建立正式记录”，避免否认已经存在的场景增量证据。

## 回归结论

修正前，实测正文的 Style Lint 状态为 `notes`，阻断数为 0。修正后，同一篇正式正文返回 `blocking`，规则为 `mechanical-contrast-frame`。故事摘要同时获得正式正文结尾，能够看到直连已经开始、载体正在读取和绕行时间增加，足以纠正旧规划摘要。

重启开发服务后的只读用户复核也通过：顶层 Agent 明确回答“交接正在进行，尚未完成”，准确指出周岑接入短接缆、许遥主动压入接口两项不可撤销动作，没有再把当前状态写成失败，也没有臆测人物性别或文风名称。

本轮结论：参考语料的类型氛围机制已经在生成中起效，人物关系和环境行动化达到可用水平；审查变体覆盖与顶层 Agent 的终态事实依据存在明确缺陷，现已用局部修正处理。生成成稿本身仍有解释潜台词、技术机关过整齐、需求清单感和熟套象征收尾等文风问题，下一轮应在生成阶段调整，不交给事后审查统一润色。

## 伪精确数字补充诊断与修正

同一篇正文还暴露出另一类稳定的模型腔：与情节因果无关的实写数字过多。正文连续给出“四小时零九分”、十五分钟、十七分钟、二十一分钟、两轮、三轮和“一寸”等数值。少数数字参与了路线选择，多数只在模拟设备专业感、实时监控感或紧迫感；读者记住的是持续刷新读数，人物选择反而退到后面。即使十五与十七分钟曾参与绕行判断，若后文不按这两个精确值验证结果，也应写成“现有窗口容不下绕行”一类直接改变选择的事实。

修正采用生成优先、审查兜底的单链方案，没有新增数字密度 Gate、阈值、正则检测或持久化字段：

- 生成阶段把精确数字设为默认不用。动态数值必须同时满足五项举证：人物需要该精度；它改变当前选择；模糊后会破坏因果；后文会验证或兑现；同一压力尚未被其他数字量化。
- 年龄、日期、规则编号等静态数值只有在身份辨认或连续性确有需要时保留，同一事实不反复报数。
- 数字已经建立压力后，正文转写人物的选择、动作和后果，不继续刷新仪表、广播、尺寸或轮次。
- 生成前后的静默检查覆盖阿拉伯数字、中文数词和序数。无法说明某个精确值改变了谁的什么选择，就围绕动作、状态变化、人物可感范围或后果逐句重写；禁止批量删数字，也禁止把精确值机械换成“很久”“一些”“许多”。
- 现有 AgentReview 只在漏网时做语义核验：精确值若没有即时因果、连续性、身份辨认或后续兑现功能，就形成可执行文风偏差。审查不数数字，也不发明配额。

这项规则与违禁表达、反规避和中文标点审查并行：后者仍由现有审查链严格核验；“数字是否必要”作为抽象文风判断，首先由生成提示落实。

## 《白塔停潮》严格规则首次回归

修正后从开发板新建《白塔停潮》，未在用户创作要求中提及数字问题，只给出台风夜、水闸故障、撤离名单遗漏和档案库代价，让模型自然面对容易滥用仪表读数与倒计时的场景。新项目挂载的文风文件已确认包含“精确数字默认不用”和五项必要性测试。

首稿候选仍出现傍晚后的三个绝对钟点、分钟倒计时、半秒、半圈和电话次数。审读修订删去了三个绝对钟点，把第一处潮位记录改成“傍晚”，证明规则已经进入链路；正式正文仍保留“一分钟左右”“半分钟”“半圈”“半秒”等无须该精度也能维持因果的表达，严格目标尚未达到。

定位到的直接冲突在场景规划：`scene_goal` 先要求“设备读数直接影响人物判断”，`revealed_info` 又要求“闸门剩余可操作时间”。生成模型把规划中的读数与剩余时间误当作数字形式授权，同时把普通时间流逝误认成后续兑现。第二次收紧不增加 Gate，而是在生成约束与现有审读提示中明确：

- 五项必要性条件缺一即去掉精度，无法确定时同样去掉。
- “后文兑现”必须按同一个精确值验证或触发阈值，普通时间过去不算兑现。
- 技术、灾难、悬疑、倒计时、场景合同中的设备读数和参考语料数字都不能豁免。
- 场景合同要求读数或剩余时间时，只落实压力和人物决策，不照抄数字形式。
- 电话次数、灯闪次数、半圈尺寸、片刻秒数、剩余分钟和重复刷新仪表，默认视为应去掉精度的高风险形态。

本轮还发现顶层回执的新事实偏差：正式正文已经写出林沅按下开闸键、档案库进水和顾桥返回，回执却称正文“在按下之前收住”。该问题与数字文风规则相互独立，记录为后续顶层事实摘要回归项，不通过本次文风补丁扩大修复范围。

## Lean-v2 根因确认：《雾岭末班》

继续从开发板新建《雾岭末班》后，正式正文仍密集出现“四十分钟前”“两次异响”“二十分钟”“五点前”“三短一长”“二号台”“五年前”“两秒”“二百二十伏”“敲了三下”“一百多号人”“两个键”等表达。这里既有连续性所需的台号，也有直接影响停运选择的信号形态，但更多数字只负责把设备、动作和紧迫感写得像记录表。已挂载文风文件确实包含最新规则，因此问题不在默认文风未安装，而在 Creative Live 的正式场景调用绕过了通用 Prompt v3 路径，实际走的是 `pi_scene_transaction.py` 中的 lean-v2 即时 create/review/revision 提示。

修正因此落在真实调用入口，而不是再增加一层检测器：create 与 revision 在 JSON 输出前执行最后的量化细节语义重写，review 在读完正文与来源后复核明显漏网项。三者共享同一条五项必要性规则；规则位于提示末端，避免被长篇 SceneBrief 与来源材料稀释。没有增加数字密度、数量配额、正则扫描、schema 字段或额外模型调用。

## 第一轮实测：《灰坝断讯》

lean-v2 首次修正后，《灰坝断讯》不再编造具体雨量、渗流值、倒计时或设备参数，还主动写出“广播里说，雨量超过设计值。具体多少，没说”，说明“压力可以明确、精度不必虚构”已经进入生成选择。

但正文仍出现“堵了一次”“一张长桌，两把椅子”“拧了两下”“试了两回”“敲了两下”“看了几秒”“一支手电”。这些数量不改变任何人的选择，也不会在后文按原值兑现。首轮规则过度聚焦仪表、时长和技术数值，模型把量词中的数词、陈设件数和日常动作次数误当成自然具体描写；审读同样因为句子通顺、有画面而放过。由此把规则补全为：量词中的数词也须过五项，普通陈设和日常动作不计件、计次或计秒，改写目标应是陈设状态、动作受阻、反复无果、停顿或取用结果。

## 第二轮实测：《冻库停电》

加强后的新项目《冻库停电》通过正式生成、审读和晋升。正文没有给温度读数、停电时长、倒计时、距离、设备参数，也没有复现《灰坝断讯》中“两把椅子、拧两下、试两回、看几秒、一支手电”式的连续记账。人物真正面对的是“先开备用机保货，还是先查库区救人”，压力落在门会锁死、冷气会散失和两人分路确认的行动后果上，不再依靠仪表不断刷新。

本轮并非数学意义上的零数字。正文还保留“两声电流杂音”和“又敲了一下”两处可继续去掉的动作计次，也有“一只工具包”“一把长柄扳手”等接近汉语不定指用法的数量短语；“两个人”“‘库区’两个字”等则承担人物范围或引语辨认功能。与《雾岭末班》的连续报数相比，绝大部分无因果精度已消失，但 AgentReview 对两处明显动作计次仍判 pass，说明软语义复核只能降低发生率，不能承诺零漏网。这一残留继续由生成提示中的严格默认规则处理，不改造成确定性门禁。

附带观察：顶层 Agent 已能在开写前说明人物、核心冲突与本场走向，在交付后说明未解决线索和下一场入口；但《冻库停电》的回执称广播只给出两个片段，正文实际还出现过“库区”，且回执仍把字数放在显著位置。前者是正文事实摘要精度问题，后者与用户已说明“字数不是重点”不一致，均与本轮数字文风内核修正分开记录。
