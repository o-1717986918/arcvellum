# 顶层 Agent 五章十万字长篇端到端验收（2026-09-22）

## 结论

本轮在开发板上以普通作者身份新建《潮痕之下》，只通过顶层 Agent 发出一次完整长篇委托，并让其自行启动、恢复、审读、发布。运行链路成功到达 `export-and-release`，生成 5 章、35 个正式场景、Markdown 与 DOCX 全书文件；顶层 Agent 的最终回执能准确说明人物结局、场景数和实际正文规模。

但本轮不能判为“十万字五章长篇质量验收通过”。更准确的结论是：

- **工程闭环通过**：规划、窗口物化、逐场生成、修订、提交、全书审计、导出与发布均走完正式路线。
- **结构数量通过**：5 章、35 场全部存在，所有场景提交回执均为 `pass`。
- **规模目标未完全达到**：正式场景正文共 92,348 个中文内容字符，距 100,000 少 7,652，完成度 92.35%；第五章仅达到本章预算的约 76%。
- **连续性与场景分工不通过**：第二、三场重复了同一次“陈砺首次来馆调卷”，并出现跨场景人物称谓碰撞。
- **当前文风修正只部分生效**：无关精确数字明显少于早期样本，但仍在全书中稳定漏出；句群节奏也呈现大面积同质化。
- **顶层交互部分通过**：开写前说明和终局回执明显改善；运行中间态仍主要是重复的系统状态卡片，不能让作者了解章节、人物和冲突如何变化。

因此，本轮证明产品已经具备“无人值守生成并交付一部长篇”的能力，但还没有证明它具备“可靠地产出一部可直接进入编辑阶段的长篇”的能力。

## 顶层 Agent 用户体验

### 做得好的部分

1. 开始执行前，Agent 能用作者能理解的语言说明林见潮、陈砺、全书核心矛盾和五章职责，不再只复述工作流任务。
2. 最终回执准确报告 5 章、35 场、92,348 字，没有把流程 `complete` 误写成“已达到十万字”。
3. 回执能说明林见潮公开父亲补签、陈砺提交正式异议、两人没有和解但继续各自劳动，也能指出正式连续性投影尚未建立。
4. 遇到两次结构化响应错误时能够自动恢复，没有要求用户理解内部协议或手工介入。
5. 阅读长卷可直接访问 35 个已晋升场景，候选稿和工程痕迹没有混入读者正文。

### 仍需调整的部分

1. **运行期信息没有作者价值。** 侧栏连续出现大量“创作 Agent / Agent 会话状态已更新 / 已完成”，但没有按章告诉用户：本章发生了什么、人物关系怎样改变、当前线索和风险是什么。开场与终局都能讲故事，中间过程却退回运行时噪声。
2. **进度口径不清。** 页头显示“全书 95%”，项目卡同时显示 `92,348 / 100,000`，终局回执又称 92%。如果 95% 表示路线完成度，就应明确标为“流程进度”；当前“全书”标签会被理解为正文完成度。
3. **“文风盲评通过”表述扩大了证据范围。** 该盲评文件生成于 00:16:37，早于长篇运行开始，评的是文风预设候选的可执行性、清晰度与复制风险，不是对 92,348 字成稿的盲评。终局回执应写成“文风预设已盲评并挂载”，不能让用户以为整部小说已经完成文学盲审。
4. **首次工具过程曾短暂泄漏英文。** 顶层 Agent 在中文说明前出现过一句英文工具过程提示；不影响运行，但破坏本地化一致性。
5. **终局回执仍把形式状态写得比文学事实更确定。** “四路线门禁全部就绪”是真实的流程事实，但没有同时提示场景相邻重复、人物别名碰撞等整书阅读问题，容易让普通作者把 formal pass 理解成文学质量通过。

建议顶层 Agent 在每章检查点只发一条作者摘要，固定包含：本章不可逆变化、两位主要人物当前立场、已经兑现/仍开放的线索、下一章压力。不要逐场刷系统状态，也不要在作者摘要中解释内部任务名。

## 文学成稿评价

### 有效部分

1. 主因果完整。替换页、失踪工人名单、补签事实、复核异议、公开上传和停工撤离形成了可以跟随的证据链，第五章确实完成了公开与后果。
2. 职业劳动大体参与了情节。揭裱、侧光、登记、复核、现场测量和证据流转不只是背景名词，许多选择通过这些劳动发生。
3. 人物代价清楚。林见潮面对父亲名声、母亲体面与职业责任；陈砺面对母亲等待、单位程序和自身曾压后报告的责任。两人的冲突不只是“一个要真相、一个要隐瞒”。
4. 结尾没有把两人强行写成和解或恋爱关系。关系停在同行而不亲近的位置，和全书克制方向一致。
5. 与早期灾难题材实测相比，正文没有持续刷新潮位、温度、倒计时和设备参数，说明“精确数字默认不用”的生成提示已经产生部分效果。

### 关键问题

#### 1. 第二、三场重复同一次首次见面与调卷

`scene_0002.yaml` 的参与者只有林见潮，局部职责是独自确认签名页背面压痕并第一次选择隐瞒；正式正文却让陈砺带调档单进入、查看同一卷宗、指出洇墨异常并离开。紧接着 `scene_0003.md` 又从陈砺首次递交同一张调档单开始，重复深色外套、反光条、胀起的卷宗封皮、签名页、墨迹/刮痕判断和流程对话。

这不是轻微回顾，而是相邻场景重复核心事件，读者会直接怀疑时间倒退或版本拼接错误。

根因位于场景合同内部：`scene_0002` 的 `participants`、`scene_goal` 和 `scene_function` 要求独处验证，但它复制了章节级 `promised_reward` 与 `payoff_or_delay`，其中又要求“陈砺来档案馆调阅同一卷宗”。模型服从了章节级承诺，提前消耗第三场事件；逐场审查没有读取上一场正式正文来检查事件唯一性和角色分工。

#### 2. 同一称谓指向不同人物

第四章 `scene_0023.md` 中，陈砺给复核组同事“老周”打电话；第五章 `scene_0032.md` 又把旧堤事故中的失踪工人称为“老周”。从上下文看这是两个不同人物，却共用同一称谓。另有 `scene_0009` 把角色资产“老工人”临时称作“刘伯”。

这类问题不是单场事实错误，而是跨场景身份跟踪失效。当前 `canon/facts.json` 和 `canon/timeline.yaml` 仍为空，主要人物 YAML 的 `known_facts` 也未写回；35 份 `scene_deltas` 虽然包含变更候选，却没有晋升为正式连续性投影。顶层 Agent 对此有所披露，但用户明确要求的“状态与连续性写回”实际上没有完成。

#### 3. 文风过度依赖程序动作和相同句法

全书最稳定的写法是：把材料摊开、按顺序排列、看一眼、停一下、放回、锁门、关灯、打电话。它适合档案/工程题材，却被 35 场反复复用，导致人物行动和叙事呼吸趋同。林见潮与陈砺虽然职业不同，语言和思维都大量使用“按流程、逐项核对、先做某事再做某事”的同一种句法，人物声音主要靠职业名词区分。

当前代码与项目档案复检还揭示了一处正式语义不一致：项目的 `creative_quality_profile.json` 把 `staccato-period-overuse` 设为 `blocking`，使用现有 `candidate_language_gate()` 复检时，35 场中有 25 场因连续短句/句号密度被判 blocking；但 lean-v2 事务验证只把硬编码的八类标点规则提升为 hard，没有按 profile 调整后的 severity 处理该规则，因此 35 场仍全部提交为 pass。这不是建议新增门禁，而是同一套既有品质档案在两条正式路径上的含义不一致。

此外，当前 AI 文风检查在 24 场留下低级 note，主要为 `plain-narration-template-sentence`；AgentReview 逐场可以接受这些句子，但整书累积后形成明显的同构节奏。整书审查不能只看“每场是否低于阈值”，还要看重复机制跨场累积后的阅读效果。

#### 4. 无关精确数字仍然稳定漏出

本轮没有回到早期连续仪表读数的程度，但严格目标仍未达到。可直接举证的漏网包括：

- 第一场：“袖口往上叠了两折”“再重半分就撕了”“是三个字”“夹进两片玻璃板”；
- 第三场：“十五个工作日”“每天来看一次”“两天来一次”“站了两秒”；
- 第四场：“闭馆广播响过两遍”“拍到第四张”；
- 场景规划本身把第九场命名为“工具车里的两分钟”。

其中少数数字参与证据辨认或制度期限，更多只是把动作、陈设和停顿写得更像记录。问题既发生在正文生成，也由规划层提前播种；AgentReview 对明显动作计次仍不稳定。后续应继续在规划和生成提示中处理，不需要新建数字密度 Gate。

#### 5. 解释性收束仍偏多

不少段落先用动作制造了潜台词，随后又补一句解释人物为何停顿、这一步意味着什么、某句话“现在不是气话”。这种解释没有达到严重模板腔，但会削弱已经成立的动作。相较之下，林见潮母亲把奖状收进柜底、陈砺母亲拿到正式受理纸的段落更有效：物件和程序后果已经足够，不需要再总结情感。

#### 6. 全书节奏与章节预算失衡

第五章承担公开、异议、撤离、名单被念出、两位主角会面、林见潮职业后果与陈砺工地余波，却是全书最短的一章。公开后的制度与家庭后果被快速并列，部分关键代价反而比前四章的查档、核表和等待写得短。第四章超预算、第五章仅达 76%，说明篇幅没有跟随剧情职责分配。

顶层 Agent 自己识别出五章张力峰值全部偏高、缺少呼吸以及重点场比例偏差；这个判断合理。下一轮若扩充，不应把字数平均补到每场，而应删去前段重复核对，给公开后的职业追责、家属承认与两人关系后果更多具体场景空间。

## 工程与状态一致性问题

### 1. 字数预算文件完成后仍是初始状态

最终 `plot/word_budget/word_budget.json` 仍记录：

- `status: needs_expansion`
- `actual_scene_count: 1`
- 五章实际场景均为 0
- `word_shortfall: 100000`

与此同时 `workflow/longform_materialization.json` 已是 5 章、35 场，发布清单也为 released。用户界面另有自己的 92,348 字投影。三处真相没有回写统一，后续 Agent 若直接读取旧预算文件，可能误判项目仍未展开。

### 2. 章节检查点事件重复且不可定位

事件流共出现 15 条 `lean_scene.chapter-checkpoint`，而实际只有 5 章。前四章检查点会在后续窗口扩展时被重复发出，形成 2、3、4、5 次的累积重复；所有事件的 `chapter_id` 都为空。第五章最后一条才携带 76% 的文本警告，也仍无结构化章节标识。

这会污染前端进度和审计日志。修复应放在现有检查点事件的幂等键和 payload 上：每个章节/版本只发一次，并携带 `chapter_id`、实际字符数、目标字符数和结果；不需要增加新检查点。

### 3. 修订统计不反映真实事务

全书实际发生 97 次 `worker.scene.revised`，`scene_0026` 单场返修 11 次；运行状态中的 `consecutive_revisions` 从始至终为 0，`stalled_cycles` 也为 0。控制层无法据此识别修订抖动，用户也看不到成本风险。

应复用场景事务已有的 `revision_attempts`，在运行投影里显示当前场次、修订轮数与最近一次实质问题；达到高轮次时改变修订策略或生成一次收敛摘要，不应通过新增用户审批门禁解决。

### 4. 正式审计范围过窄

`review-and-audit` 与发布清单都判 pass，但没有阻止：

- 相邻场景重复核心事件；
- 同一人物称谓指向两个角色；
- 连续性投影为空；
- 既有品质 profile 与 lean 验证严重度不一致；
- 章节导出重复章号；
- 字数预算仍停在初始状态。

正式 pass 因而只证明结构文件和路线条件满足，不能作为整书文学质量通过的同义词。顶层 Agent 的用户回执需要明确区分这两类结论。

## 建议修正顺序

本轮没有修改源代码。后续实现建议保持现有内核，不增加新的文学门禁或第二套状态机。

1. **先修场景合同冲突。** 物化场景时不要把章节级 `payoff_or_delay` 原样复制到每个场景；生成与审查明确以本场 `participants`、`scene_function`、`scene_turn` 为局部边界。把上一场正式正文尾部、上一场已兑现动作和下一场保留事件放进现有相邻上下文，审查时检查“本场是否偷跑下一场”。
2. **完成现有 scene delta 写回。** 复用 35 份 `workflow/scene_deltas`，把批准后的角色变化、事实、时间线和称谓映射写入已有 canon/character/continuity 资产；不再让它们长期停留为候选侧车。
3. **让规划也执行数字软约束。** 场景标题、目标与 revealed info 不要无必要地注入“两分钟、两遍、第四张”等形式；生成提示继续做五项必要性判断，审查只处理明显漏网，不新增数字计数器。
4. **统一既有品质档案语义。** lean-v2 验证应尊重 `lint_punctuation()` 已经按 profile 调整后的 severity，或与现有 `candidate_language_gate()` 共用同一判断函数；这是消除双重口径，不是加强门禁。
5. **收敛修订循环。** 将事务 `revision_attempts` 投影到 Autopilot；高轮次改用“固定剩余问题清单 + 最小修订”，避免每轮审查重新发明标准。保留现有自动恢复，不把普通返修升级为人工审批。
6. **修检查点幂等与用户摘要。** 每章只产生一条带章节 ID 的正式检查点事件，同时让顶层 Agent 输出一条故事摘要；前端不要逐场堆叠相同状态卡。
7. **统一完成态投影。** 在正式发布前刷新 word budget 的实际章节、场景和字数数据；UI 分开显示“流程进度”和“正文规模”，导出器去除重复章号。
8. **校准终局回执证据范围。** “文风预设盲评通过”和“全书文学审读通过”必须分开；回执继续报告实际字数、人物结局和未写回连续性，不以 formal pass 覆盖成稿问题。

## 下一轮验收标准

下一轮仍应由顶层 Agent 单次委托完成，不手工修正文稿：

- 5 章、35 场、正文接近 100,000；若使用“约十万字”，建议目标区间至少达到 95,000–105,000，并如实报告；
- 无相邻场景重复同一核心事件，无场景提前消耗下一场职责；
- `participants` 与正式正文出场角色一致，新增称谓不会与现有人物碰撞；
- scene delta 中的已批准事实可在正式连续性/人物状态中查询；
- 数字精度只保留真正改变选择、身份辨认、连续性或后续兑现的部分；
- 现有 profile 对同一正文在 lean 事务和 promotion 检查中得到一致结论；
- 每章仅一个带 `chapter_id` 的检查点事件；
- 顶层 Agent 每章提供一次人物与剧情进展，不再展示一串相同的“状态已更新”；
- 分章和整书导出章号不重复，预算文件、UI、发布清单与顶层回执使用同一实际字数；
