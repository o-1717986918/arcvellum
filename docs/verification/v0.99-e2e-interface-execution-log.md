## 2. GitHub Issue #20 归因

Issue 截图暴露的是跨模块产品故障，不是一条错误文案：

| 现象 | 责任模块 | 必须修复的根因 |
|---|---|---|
| Prompt `67021 > 48000` | Prompt Program / Evidence Projection | 编译前预算、按任务裁剪和可行动的超限诊断 |
| `repair timeout` | Runtime Provider Reliability / Repair | 独立 repair timeout、错误分类和有限恢复 |
| `no-progress guard stopped...` | Pi Worker / Autopilot Progress | 区分模型无产物、重复工具错误和正式项目无进展 |
| sidecar 提醒重复刷屏 | Advisor Inbox / Notification Deduplication | 以阻断身份和 revision 去重，状态变化后再提醒 |

内部异常原文保留在诊断日志和高级观测中；普通界面只展示稳定错误代码、中文说明和可执行动作。

## 6. E2b 批次计划：Pi Worker 多产物落地协议

真实基线在 `character-and-world-assets-world-foundation-asset-review-pass` 暴露了一个可复现的运行时协议缺陷：模型已经提交四个 Agent-owned 产物，但首轮超长批量工具参数被 Provider 截断，其中世界规则 JSON 留下语法错误；随后模型在同一响应中逐文件调用四次 `validate_output`，首个校验改变了全局协议阶段，导致其余三个兄弟调用被错误拒绝，并在第六轮耗尽预算。

本批按 Runtime 模块边界修复，不增加轮次来掩盖问题：

1. `write_expected_output` 每次写入后自动运行全量本地校验，并把聚合错误返回模型；
2. `validate_output(path)` 可以返回单文件结果，但 Worker 的内部状态始终保留全量聚合结果，避免最后一个通过的单文件覆盖其他失败；
3. 一次 Provider 响应开始时冻结该响应的 required-tool lease，同一响应中的兄弟工具调用不因前一调用改变状态而被误拒绝；
4. 多产物写入提示明确限制超长 batch，优先按一个完整产物一次提交，避免工具参数在 Token 上限处被截断；
5. 增加“截断 JSON + 多文件 + 最后一轮修复”的 Worker 回归测试，再恢复真实 E2E 基线验证。

完成标准：相同四产物任务在一个 JSON 语法错误时得到精确修复机会；无效兄弟调用不消耗为协议冲突；全部产物本地有效后仍由 Studio 正式预检裁决。

### E2b 实施记录（2026-08-20）

- 写入工具现在立即返回全量聚合校验，截断 JSON、缺失兄弟产物和提交来源问题都能在同一轮被模型看到；
- 单文件 `validate_output` 不再用局部通过结果覆盖全局失败状态；
- required-tool 改为 Provider 响应级 lease，同一响应中的兄弟调用不会因先执行调用改变状态而被误判为越权；
- 主创 Worker 取消“所有产物必须首轮批量提交”的危险指令，超过 12000 字符的多产物任务按完整文件逐项提交；
- Pi Worker 46 项测试、Python Runtime/合同 24 项测试及架构审计通过，未增加依赖违规或循环。

真实 E2E 复验尚未完成；本批提交后恢复原运行，只有穿过原 `world-foundation` 修订门禁才算关闭该阻断。

## 7. E2c 批次计划：审查 Agent 的读取到提交收敛

E2b 后原 `asset-review-pass` 已完成并进入新一轮独立 `asset-review-agent-task`，证明四产物修订阻断被解除。随后审查 Agent 连续两轮调用 `read_task_context`：第一轮实际完成了长篇语义分析，第二轮又重新读取同一合同；由于合同读取没有进入 Worker 进度指纹，no-progress guard 将其误判为两个完全相同的空转回合。

本批修复：

1. 将任务合同读取次数纳入 Worker 状态和进度摘要；
2. 非正文 Agent 保留一个证据读取响应，一旦读取任务合同或任一按需资料，下一 Provider 回合强制进入 `write_expected_output`；
3. required-tool 阶段误用改为可纠正的非终止工具错误，避免供应商忽略 tool choice 时直接结束会话；
4. 保持 Studio 正式预检、独立审查身份和失败闭锁不变；
5. 以审查 Agent “读取一次后必须写入”的单元测试和原项目恢复运行验证闭环。

### E2c 实施记录（2026-08-20）

## 8. M1 批次计划：唯一应用组合根

实际代码复核确认 M1 尚未实现：`api_server.create_app()` 直接构造 Lifecycle、Bootstrap、Advisor 与 Autopilot；`ApplicationLifecycleManager` 直接构造 JobStore、事件总线、缓存、进程管理器、Runtime Pool、Coordinator 与 Supervisor；`_STYLE_MOUNTS` 是跨 App 共享的模块级可变服务。

本批边界：

1. 新建 application-owned ports，接口仅覆盖生命周期真正使用的能力；
2. 新建 infrastructure 默认适配器装配，保持安装版路径、线程数、缓存和 Runtime 行为不变；
3. 新建 `ApplicationContainer`，统一持有 config、ports 与 lifecycle/bootstrap/advisor/autopilot/style services；
4. `ApplicationLifecycleManager` 只接收 ports，不再导入或构造具体基础设施；
5. `create_app(config_override=None, container=None)` 只消费 container 并装配 HTTP 路由；
6. 删除 `_STYLE_MOUNTS`，每个 App 拥有独立 Style 服务和 Cache；
7. 保留旧 `literary_engineering_studio.lifecycle.ApplicationLifecycleManager(config)` 兼容入口，但兼容装配不进入 application 层；
8. 增加双 TestClient 隔离与内存/替身 port 测试，执行 API、生命周期、Style、架构审计和全量必要回归。

完成标准：`application/lifecycle.py` 不依赖 concrete infrastructure；两个 App 不共享 Style/Cache；默认桌面与开发服务器行为不变。
