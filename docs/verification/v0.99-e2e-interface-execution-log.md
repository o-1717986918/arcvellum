## 1. 不可替代的验收证据

真实闭环必须同时证明：

1. 作品通过公开 Studio API 创建并记录创作方向；
2. 使用内置 `pi-worker` 和用户已配置的模型连接启动 `full_auto`；
3. 长篇规划物化两章、六场正式合同；
4. 每场正文均经过候选生成、独立审查、晋升、状态写回和连续性写回；
5. Reader 投影的正式正文不少于 30000 个中文内容字符；
6. Autopilot 正式完成，而不是测试脚本提前暂停；
7. `export-and-release` 无阻断并生成至少一个可下载正式文件；
8. 运行记录包含真实 Provider 请求与 Pi Worker 会话。

原有 `first-loop` 验收继续保留，用于快速验证第一场到下一场的衔接；它不能代替本轮 `full-work` 验收。

## 2. GitHub Issue #20 归因

Issue 截图暴露的是跨模块产品故障，不是一条错误文案：

| 现象 | 责任模块 | 必须修复的根因 |
|---|---|---|
| Prompt `67021 > 48000` | Prompt Program / Evidence Projection | 编译前预算、按任务裁剪和可行动的超限诊断 |
| `repair timeout` | Runtime Provider Reliability / Repair | 独立 repair timeout、错误分类和有限恢复 |
| `no-progress guard stopped...` | Pi Worker / Autopilot Progress | 区分模型无产物、重复工具错误和正式项目无进展 |
| sidecar 提醒重复刷屏 | Advisor Inbox / Notification Deduplication | 以阻断身份和 revision 去重，状态变化后再提醒 |
| 用户不知道如何补设定 | Recovery Guidance / Onboarding | 错误卡给出中文原因、影响、系统可自动做什么和用户下一步 |

内部异常原文保留在诊断日志和高级观测中；普通界面只展示稳定错误代码、中文说明和可执行动作。

- 每批保留输入、输出、错误语义和回滚点；

- 每个批次更新本文，执行定向测试、架构审计并创建独立 Git 提交。

## 5. E2 批次计划：故障呈现与恢复合同

本批只改“错误如何跨模块流动”，不改文学 Gate、任务顺序或正式写回规则：

1. 在应用层建立版本化 `FailurePresentation`，统一稳定代码、类别、用户标题、中文说明、影响、恢复动作与诊断原文；
2. Runtime/Prompt/Autopilot 的原始错误先分类，再将用户可读投影写入运行状态；诊断事件继续保留原文；
3. Autopilot 状态 API 同时保留兼容字段 `last_error`，并新增结构化 `failure`，避免前端继续猜测字符串；
4. 顾问 Inbox 以 `failure.code + route + task/revision` 去重，不再因 sidecar 数量或原始措辞变化重复刷屏；
5. 前端以恢复卡展示原因、影响和下一步；高级详情可以展开技术诊断；
6. 为 Issue #20 的 Prompt 超限、repair timeout、no-progress 和 sidecar 阻断建立回归测试。

完成标准：普通界面不再直接显示 Issue #20 截图中的英文内部异常；同一阻断不会重复制造提醒；已有 API/客户端兼容测试继续通过。
