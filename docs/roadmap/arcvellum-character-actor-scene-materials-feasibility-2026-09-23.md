# 场景角色表演与多 Agent 素材机制：可行性与工程方案

> 2026-09-23；决策稿，不是已实施功能。以三场实际创作、真实 Prompt、现有模块边界和公开研究为依据。

## 结论先行

值得试验“导演约束下的角色表演”，但不建议把对白、人物动作、环境描写拆成三个互不相干的正文写手。对白与动作共同构成潜台词；环境描写也依赖视角人物注意什么、故意漏掉什么。机械拆分后再拼接，容易产生声调接缝、重复动作和无主的气氛段。建议以当前主创 Agent 为场景导演兼最终作者，让**一个角色表演单元同时提出该人物的说法与行为**；环境单元先提供可用的空间阻力、物件与感知素材，不直接包办成段正文。只有盲评证明素材单元确实优于单 Agent 排练时，再把它们升级成正式的场景局部 Agent。

本项目还有一条先决约束：现行 `AGENTS.md`、开发标准和外部项目技能明文规定正文只能由正式主创 Agent 写，subagent 不得代写正文。用户提出的“角色 Agent 产出具体对白和动作”与之直接冲突。不能仅在 Pi Worker 内私加子会话就上线；若确认采用，须先明确修订宪法，将“非正式、可拒绝的场景素材”与“正式正文”区分，并由 Engine TaskPackage 授权，保证主创仍为唯一正文作者、审查和晋升不变。

## 一、真实问题不等于“缺少 Agent”

隔离测试《岸外来信·文风样本》三场已生成：前两场正式正文，第三场候选通过生成与审读但停在高风险批准点。创作链技术上投射了参考；文学质量没有通过。第二场的真实 `Scene Create` Prompt 约 30,143 字符，其中 `Relevant Sources` 约 21,000 字符，选中参考约 250 字符。错误的 R23“密闭恐惧”选段被投射到面馆证人对话；这是选择器取用了章级未来线索及过宽的“广播”标签，而不是角色扮演能力问题。该缺陷已在新代码修正，但旧不可变挂载不改写。

成文里，人物可辨的职业语汇有了，却共享“流程、记录、签名栏、核对”的说明性逻辑；第一场大量登记动作、绳结和设备步骤，第二场下颌、纸张、铅笔、杯子反复承担同一种停顿。第二场“三十年了”还与规划“停播十年”矛盾。现有场景模板固定要求“每段至少承担行动推进、信息改变、关系压力、选择代价或场景衔接之一”，三场环境比例都设 `low`；这会诱导模型把审美停留写成可交代的手续。这里的因果仍需消融验证，不能把一轮读稿写成确定性实验结论。

Pi Worker 并未暗藏禁止文风的系统词：`workers/pi-worker/src/conversation.ts` 的 role conversation 系统提示只规定无工具、无项目写权限、遵守任务合同；lean 正文由 Studio 的 `PiSceneTransactionRuntime` 通过这个通道生成完整 JSON。真正的风格压力主要来自它收到的 `SceneBrief`、约束密集的场景 Prompt、模型能力及选段错配。正式任务 Worker 的 `main-creative-agent.md` 又要求第一动作立即 `write_expected_output`，不给聊天式排练阶段；它管的是正式任务工具流程，不应直接在这里堆更多文学禁令。Pi stream 当前没有向模型请求传入可核验的 temperature 参数；“调高温度”不是这次失效的已验证修复。

## 二、提议逐项评估

| 提议 | 价值 | 主要风险 | 本项目建议 |
| --- | --- | --- | --- |
| 人物对白交给角色 Agent 具体说出 | 高。可把身份、知识边界、当前欲望落实在句子里，尤其是试探、争执、言不由衷 | 只给性格标签会产出口头禅；只给指定台词会原样复述；自由表演又可能偏离剧情 | 用场景节拍与言语行为任务单，指定“要完成什么话语动作”，不预写台词；角色输出候选，主创可拒绝 |
| 人物动作再交给另一 Agent | 中低。动作确能体现个人习惯 | 与对白分离后潜台词断裂，重复摸杯、看手、抬下颌等安全动作 | 与角色对白同一表演单元生成；仅约束物理可行性、动作目的和可见后果 |
| 环境描写交给专门 Agent | 有条件。可补空间使用、质感与场景阻力 | 独立散文段容易变天气/灯光/气味轮播，侵蚀叙述视角；R23 式气氛错配可被放大 | 先做可选“场景材料顾问”：给出 2—4 个与人物视角和当前行动相关的物件/声源/通路/阻碍，不直接写完整段落 |
| 主创 Agent 组织素材并补写 | 必需。统一叙述距离、信息释放、节奏和事实责任 | 若只是机械拼接，会出现多声部缝隙和冗余解释 | 主创保有删、改、重写素材的权利；最终正文必须由主创重新成篇，而不是拼贴 |

相关研究提供了可试验的方向，但没有证明它一定改善中文长篇小说。[Yu 等的角色模拟研究](https://aclanthology.org/2025.in2writing-1.9/)把“按计划角色扮演”与“重写成文”分开，报告优于两个 LLM 基线，但主要使用 LLM 自动评估。 [IBSEN](https://aclanthology.org/2024.acl-long.88/)提出导演—演员协作，也明确指出给演员现成台词易导致照抄，放任演员又会偏离目标，因而改用高层行动指令。 [StyleRPA](https://arxiv.org/abs/2411.02457)提示角色事实与角色语言风格是不同能力，语言样本比抽象人格标签更有用。 [Dramatron 团队的实际使用说明](https://google-deepmind.github.io/dramatron/details.html)同时提醒模块化有助于共同创作，但输出可能程式化，且未被当作自治成稿系统验证。文学仿写研究也显示给样本可改善局部风格相似度，却仍可能保留通用模型腔；不能用“已引入样本”代替读者检验。[风格模仿实证](https://academic.oup.com/dsh/article/40/2/587/8118784)

## 三、建议的最小可行架构

```text
已确认的场景剧情、人物/世界状态、表达计划
                   ↓
主创制作带 beat_id 的场景任务单
                   ↓
按需要调用角色表演：一个人物的一次言语行动 + 连带动作
                   ↓
可选场景材料顾问：空间阻力、物件、感知机会（非成段正文）
                   ↓
主创选择、拒绝、改写素材并写成完整场景
                   ↓
现有硬语言审查、语义审读、Canon/状态晋升
```

每张角色任务单应固定：`scene_id/beat_id`、人物身份与关系、此时已知/误知、公开目标与不愿承认的目标、必须完成的言语行为、必须留下的对方反应或信息差、允许的动作范围、不得新增的事实，以及人物专属语言样例与反模式。所谓“要说什么”应固定**信息与行动的功能**，不能先写标准句；演员只在个性化措辞、回避路径、节奏、礼貌边界、幽默和动作时机上创造。输出可是一至两组候选 `spoken`、`visible_action`、`subtext_effect`；不输出完整场景，不作 Canon 判定，不写项目文件。需要延续对话时按节拍顺序给演员上一轮真实台词，而不是让几个人并行猜测彼此会说什么。

人物声音资产不宜只加“更尖刻、更幽默”标签。现有 `speech_style` 的词域、节奏、禁词和标志性句式可保留，但还需要少量**跨处境的声音实例**：轻松、受逼、撒谎、对亲近者、对陌生者各一句，由用户或主创确认。实例用于表演，不作为必须复读的口头禅。场景任务单的“当前言语行动”优先于永久性习惯：同一人物受压后可以变调。环境材料也需标记“谁感知、为何此刻被注意、若删除是否影响空间/情绪/因果”，避免独立景物作业。

## 四、先做消融，再扩 Runtime

最小实验采用同一批八类场景、固定 Canon/模型/预算/参考版本、盲化展示，逐组比较：A 当前单 Agent；B 不增 Agent，只把场景任务单改成主创内部角色排练并减轻“每段必须推进”等偏置；C 在 B 上加入真实角色表演候选；D 在 C 上按需加入场景材料顾问。A 的旧成稿是历史基线，B—D 应同一轮同模型重新采样。至少三位读者分别评价去名对白辨识、关系张力、叙述起伏、环境是否从视角生长、整体继续阅读意愿，并引用原文；另记剧情偏离、Canon 错误、重复动作、调用次数、耗时与费用。只有 C 对 B 稳定胜出，且不显著增加事实错误时，才启用角色 Agent；只有 D 对 C 胜出，才启用环境单元。软审美不增静态阻断门禁，违禁词、标点和 Canon 审查继续保留。

首先应在 B 组处理目前可观察的输入偏置：选段只看当前场景，参考和人物声音放在正文写作动作附近；把“每段必须推进”改为允许有目的的审美停留；不要让 `description_ratio=low` 成为一切场景默认值；对比当前 flash 模型与更强创作模型，在同一 Prompt 下看质量上限。温度实验后置并要求 Runtime 报告实际生效参数；[温度与叙事创造力实验](https://arxiv.org/abs/2405.00492)发现升温只弱相关于新颖度，却更易损害连贯，不能作为主方案。

## 五、模块落点与准入条件

**不新建跨层“大创作模块”，不让 Pi Worker 拥有文学决策。** Engine `literary/scene/roleplay/` 可拥有角色任务单、知识边界与素材候选 schema，`public/literary.py` 只暴露稳定构建/验证接口；Studio `runtimes/pi_scene_transaction.py` 在 lean-v2 的场景事务内执行可选的 role conversation、缓存候选与 provenance，再把候选作为非权威资料交给主创。`workers/pi-worker/src/conversation.ts` 只需支持一个白名单化的 `character-actor`/`scene-material` 会话配置（若现有通用系统提示在实验中不足），不建立新 Provider 层、不赋项目写权限、不直接管理 Canon。正式路线若证实受益，应在现有 `scene-development` Route 中增加 Engine 签发的场景素材 TaskPackage/expected outputs，主创的 prose task 显式读取该 sidecar；不另造顶层 Route、第二套审查或第二个正文 writer。Creative Live 只读显示素材采用/拒绝与来源；UI 提供默认关闭的实验开关、成本上限及回退。

在上述 C/D 试验或产品实现前，需先提交并让维护者确认一份宪法变更：允许**隔离、非正式、不可直接晋升**的角色对白/动作候选由专门 Agent 生成；正式正文、返修、审读和分支决定仍只归主创及现有路线，角色 Agent 无工具和项目写权限。同步更新 `AGENTS.md`、开发标准、项目技能和正式 Host 宪法，补合同测试证明素材不能直接成为正文或 Canon。这不是纯技术重构，而是创作责任边界改变；在批准前，只实施 B 组单 Agent 排练与既有选段修复。

若 C/D 没有实质读者优势，删除实验 sidecar 与角色调用入口，保留有用的任务单、角色实例和提示词修正。这样回滚单位清楚，也不会把多 Agent 数量本身当成产品目标。
