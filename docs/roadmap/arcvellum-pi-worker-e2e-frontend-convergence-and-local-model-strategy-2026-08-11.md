# ArcVellum Pi Worker 端到端验证、前端收敛与本地模型策略

日期：2026-08-11
状态：v0.97.4 发布验收依据
范围：Pi Worker、Studio Runtime、叙事星仪、空间窗口、本地模型路线

## 1. 结论先行

本轮验证证明了三件事：

1. Pi Agent Core 适合被构造成 ArcVellum 的专用、受约束文学 Worker。它不需要继承通用 Coding Agent 的完整权限，也能完成规划、角色推演、正文候选与独立审查。
2. 现有 Studio 的确定性 Gate 仍然必须保留。模型写出文件不等于任务完成，Style Lint、schema、精确候选审查、晋升与状态写回仍应由 Studio 收束。
3. 完全用单一小型本地模型替换全部创作模型，当前不能满足 ArcVellum 对长篇正文、文风、复杂因果和独立审查的质量要求；按任务能力路由的混合方案可行。

本轮可以发布的是“Pi 专用 Worker 的实验性闭环与前端可靠性增强”，不能宣称 Pi 已经成为默认、零配置、整本书无人值守的生产 Runtime。

## 2. Pi Worker 真实闭环证据

### 2.1 模型任务矩阵

使用同一套 Pi Worker 原型、真实模型连接和 Studio TaskPackage 完成了以下验证：

| 环节 | 结果 | 耗时 | Token / 成本 | 关键结论 |
|---|---:|---:|---:|---|
| 长篇规划 | 通过，等待写回 | 38.22 秒 | 28,558 / $0.002129 | 结构化规划任务可由专用 Worker 完成 |
| 角色推演 | 通过，等待写回 | 56.84 秒 | 116,029 / $0.006257 | 能完成 RP，但旧提示词存在 24.08% 重复上下文 |
| 正文生成 | 通过，等待写回 | 90.03 秒 | 259,018 / $0.016198 | 精确状态授权修复后正文任务可执行；v2 提示词仍过重 |
| 候选审查 | 通过，等待写回 | 74.87 秒 | 56,413 / $0.004776 | 回合预算边界修复后，可在 6 回合约束下完成正式审查 |

这些任务来自可复现的真实 TaskPackage 基准切片。它们覆盖模型侧的创作主链，但不是一次运行中的同一个项目连续写回，因为基准切片按审批边界隔离。后半段由确定性端到端测试覆盖：候选只有在 Style Lint、语义审查、候选摘要和晋升证据全部通过后才能进入正式正文。

### 2.2 本轮修复的系统性问题

#### 回合预算边界误判

旧 Worker 在最后一回合已经写出全部产物并通过本地验证后，仍可能因为没有多余回合调用 `complete_task` 而报失败。

修复后：

- 回合耗尽时执行一次本地最终验证；
- 产物通过则以 `turn_limit_validated` 收束；
- 产物不完整则继续失败关闭，不把半成品伪装成成功。

#### Studio 预检与 Worker 本地验证断裂

旧链路只知道“Worker 写完了”，不知道 Studio 的权威预检是否通过。正文偶发一个标点或 Style Lint 问题时，整个昂贵会话直接失败。

修复后：

- Studio 对 Worker 产物执行权威预检；
- 失败时生成带问题摘要、精确文件和 digest 的有界修复包；
- 使用新的短进程在同一沙箱修复，不重新发送完整任务；
- 相同错误 digest 重复出现时立即停止，防止修复空转；
- 通过后仍由原有 `task-submit`、`task-complete` 和 Gate 收束。

#### 状态授权过窄

原型曾把允许状态写死为三个 canary state，导致正文的 `candidate-generation-provenance` 被错误拒绝。

修复后由 Studio 对每个进程只授权当前 `task.current_state`。它既允许新增正式状态，也没有把 Worker 放宽成任意任务执行器。

## 3. 前端批判性审查

### 3.1 已成立的设计优势

- “叙事观测仪器”视觉方向鲜明，没有退化为通用管理后台。
- 项目标题、星仪、章节长卷、健康轨、人物线和关系镜头形成了可识别的产品语言。
- 正式正文、Agent 会话、规则、决策和交付都已有真实数据入口，不是展示性空壳。
- Markdown 渲染、正文阅读器、空间窗口、主题和关系镜头已形成完整交互骨架。
- 窄屏会自动回到线性工作区，避免强行把 2.5D 场景压缩成不可操作的小地图。

### 3.2 本轮发现并修复的问题

#### P0：窗口越界与历史布局失效

窗口位置会持久化，但视口变小后只做单窗 clamp，不重新处理多窗碰撞。规则窗因此可能被裁到屏幕外。

修复：

- 增加视口变化后的统一重排；
- 三窗以内使用基于碰撞面积和偏好距离的放置评分；
- 四窗以上进入三列紧凑布局，并按最小可用尺寸收束；
- 放不下的窗口进入已收起栏；
- 窄屏只保留最高层活动窗口；
- 工具栏新增“整理”命令，用户可主动恢复工作台秩序。

#### P1：关系线重复绘制

Pixi 氛围层和 SVG 交互层都绘制了证据、承诺与人物关系，大项目会把同一关系画两遍。

修复：

- Pixi 只保留章节/场景主干和桥接线；
- 证据、伏笔、审查和人物关系统一交给 SVG 交互层；
- 高密度项目降低未聚焦关系的发光和动画成本；
- 所有关系仍在，聚焦、人物选择和关系镜头仍能恢复完整高亮。

#### P1：密集仪表的可读性

部分窗口正文与标题字号低于长期阅读的舒适范围。

修复：

- 标题与说明文字小幅增大；
- 保留紧凑信息密度，不扩大卡片和装饰面积；
- 规则、Agent、推进继续使用内部滚动，不让窗口无限增长。

#### P0：大项目初始化重复计算

应用外壳与总控页面会在挂载阶段同时请求同一作品的工作区快照。小项目下几乎无感，但连续视觉验收中的千场景项目会重复执行昂贵投影并长期停在“正在建立叙事场域”。

修复：

- Store 对同一作品的并发工作区刷新做单飞合并；
- 所有调用者共享同一 Promise 和快照结果；
- 保留两处初始化入口的故障恢复能力；
- 开发服务器显式绑定 `127.0.0.1`，统一 Vite、API 代理与 Playwright 的网络地址。

### 3.3 后续前端重构建议

以下问题存在，但不应为了本次发布进行大面积重写：

1. `parallaxRenderer.ts` 仍接近千行，应按 atmosphere、relations、foreground、projection 四个职责拆分。
2. `AdvisorDock.vue` 同时承担会话、拖动、流式消息和控制台命令，应拆为会话壳、消息流和命令桥。
3. 多套历史 CSS 仍并存。应先建立 token/组件使用清单，再删除重复选择器，不能直接做视觉“大扫除”。
4. 关系密度目前按总边数分档。下一步应加入“屏幕空间占用率”和帧耗时反馈，而不是只看数据量。
5. 空间窗口布局应增加可保存的用户工作区预设，例如“写作”“审查”“阅读”“运营”，减少反复开窗。

## 4. Pi 可扩展方向

### 4.1 高价值扩展

1. **能力限定的角色 Worker**：规划、RP、正文、审查、连续性各自拥有不同工具和预算，不再使用一套通用提示词。
2. **只读上下文子 Agent**：多文件读取可并行，但子 Agent 只返回带来源的摘要，不写正文、不写正式项目文件。
3. **章节级持久会话**：一个章节共享经过批准的上下文 digest，场景之间只增量更新，避免每场重发全项目。
4. **事件流协议**：Pi 把读取、推理阶段、工具调用、验证、修复和预算持续推送到前端，执行中心不再只显示“仍在运行”。
5. **Creative Plan Compiler**：总监 Agent 生成受 schema 约束的创作 DAG，Studio 注入不可删除的 Gate 后编译为 TaskPackage。
6. **比较式创作**：高价值场景可并行生成两个短候选，由独立评审只比较关键段落，胜者再扩写，避免整场多稿浪费。
7. **模型能力评估路由**：以任务历史通过率、修复次数、成本和延迟选择模型，不按模型名称做静态假设。

### 4.2 能带来质变的流程调整

#### 从“每个任务重新理解全项目”改为“批准事实编译”

建立只包含已批准 Canon、人物状态、章节义务和当前场景合同的 `Creative Context Capsule`。模型默认只读 Capsule；需要原文证据时再按路径读取。这样同时降低 Token、冲突和错误引用。

#### 从“整场生成后审查”改为“两段式生成”

先生成场景的不可见结构稿：节拍、信息释放、情绪转向、段落预算和衔接。结构通过后再写正文。正文失败时优先局部重写段落，不重做 RP 与分支。

#### 从“审查是一篇长意见”改为“可执行差异”

审查输出应优先形成：问题位置、违反合同、最小修订边界、禁止替代写法、复核条件。只有文学判断无法结构化时才附长评。

#### 从“所有任务串行”改为“读集并行、写集串行”

人物资料摘要、历史事实检索、节奏审计和承诺账本检查可以并行；正文、Canon 写回、状态应用和晋升继续串行。并发前必须进行读写集冲突检查。

## 5. 全本地小模型可行性

### 5.1 不建议的方案

用一个 7B 或 14B 本地模型同时承担：

- 百万字上下文理解；
- 长篇规划；
- 高质量正文；
- 文风拟合；
- 独立语义审查；
- Canon 与状态裁决。

这会把当前流程的结构可靠性保住，却显著降低文本质量、隐含因果判断和审查独立性。较弱模型还更容易在长任务中重复读取、遗漏工具完成调用或用格式正确的空洞内容通过表层 schema。

### 5.2 可行的混合分工

| 模型级别 | 适合任务 |
|---|---|
| 本地 7B-14B | 分类、抽取、上下文路由、账本候选、格式修复、lint 解释、项目问答 |
| 本地 14B-32B | 受限规划草案、RP 初稿、分支展开、二级审查、资料归纳 |
| 强云模型或更大本地模型 | 正式正文、复杂文风、关键修订、顶层文学判断、接近分数的分支裁决 |

最终应由 Capability Broker 根据实测通过率自动升级：小模型先做，失败或质量分不足时再交给强模型。用户可以选择“全本地”，但界面必须展示预期质量、速度和硬件代价，不能把它包装成无损替换。

### 5.3 全本地达到要求的前提

- 本地模型至少通过 ArcVellum 的任务级评测集，而不是只看参数量；
- 支持稳定结构化工具调用；
- 有足够上下文窗口和 KV Cache；
- 正文与审查使用不同模型或不同评价器，避免同源盲点；
- 允许高风险任务触发用户复核；
- 提供可选的云端升级通道。

## 6. 发布门槛

本轮发布前必须满足：

- Pi Worker 单测和 TypeScript 构建通过；
- Studio Pi Runtime、修复协调器与确定性晋升端到端测试通过；
- Studio 全量 Python 测试通过；
- 前端全量 Vitest、类型检查和生产构建通过；
- 1280×720 大规模项目视觉验收通过；
- 窄屏回退界面无窗口叠压；
- Windows sidecar provenance、桌面构建和版本同步通过；
- Release 明确标注 Pi Runtime 为实验能力，不自动替换稳定 Runtime。
